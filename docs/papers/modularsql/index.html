ModularSQL · Research paper

ModularSQL: A Runtime Guardrail for the Multiplicity Blind Spot in Text-to-SQL

Tianxin Zhou · Ruixi Lin

arXiv preprint · 2026arXiv:2609.29573

Abstract

Author-written abstract from arXiv:2609.29573v1.

Text-to-SQL systems are increasingly deployed on production databases, where queries that pass benchmark evaluation can still produce results that distort downstream workflows. Standard set-based execution accuracy (Set-EX) collapses duplicate rows and can therefore miss multiplicity errors, including missing DISTINCT, inflated aggregates, and Cartesian-style join explosions. We call this the Multiplicity Blind Spot (MBS) and introduce Multiset-EX, a multiplicity-preserving evaluation criterion that exposes such failures. Across released DeepEye-SQL artifacts from three backbones (Qwen2.5-Coder-32B, Qwen3-Coder-30B-A3B, and Gemma-3-27B) on executable BIRD-Dev N=1532, we find a consistent 5.81--6.79 pp gap between Set-EX and Multiset-EX. The gap is not specific to DeepEye-SQL: it persists on released DAIL-SQL+GPT-4 (5.22 pp) and BIRD GPT-3.5-turbo (3.39 pp) predictions. We further introduce ModularSQL, a lightweight post-selection runtime guardrail that probes executed results for multiplicity anomalies and applies deterministic patches or low-cost LLM rescue only to flagged queries. Integrated with DeepEye-SQL using Qwen3-Coder, ModularSQL preserves Set-EX at 72.06% while improving Multiset-EX from 65.86% to 67.75% (+1.89 pp). It flags 77 high-risk anomalies, while adding only $0.0076 in total LLM cost and 120 ms amortized latency per query. Cross-pipeline evaluation shows that the candidate-free detector and deterministic patches also transfer to independently released prediction sets. Overall, these results show that benchmark accuracy does not necessarily imply execution-safe SQL, and that lightweight, multiplicity-aware runtime guardrails can narrow this gap with modest computational overhead.

Research question

ModularSQL checks executed SQL results for multiplicity problems that set-collapsing evaluation can miss. It combines a duplicate-preserving metric with selective runtime intervention.

Method & reported findings

  • Multiset-EX retains duplicate counts while ignoring row order. A post-selection detector triggers deterministic DISTINCT patches or candidate-based LLM rescue. Source: v1 §2.2, v1 §3
  • Across three released DeepEye-SQL backbones, Set-EX exceeded Multiset-EX by 5.81–6.79 percentage points on 1,532 executable BIRD-Dev queries. Source: v1 Table 1
  • The Qwen3-Coder reproduction improved Multiset-EX from 65.86% to 67.75%, preserving 72.06% Set-EX. In the reported 1,532-query run, it flagged 77 anomalies, with $0.0076 total additional LLM cost and 120 ms amortized overhead per query. Source: v1 Table 3, v1 §4.5, v1 §4.6

Scope & limitations

  • Experiments cover BIRD-Dev with SQLite. Full candidate-based rescue was tested only with the DeepEye-SQL reproduction; candidate-free components transferred to two other released prediction sets.
  • Deterministic patches address DISTINCT changes, not general aggregation or join repair. No additional full repair-round comparison was performed.

Researcher questions

Why can text-to-SQL execution accuracy miss duplicate-row errors?

Set-based comparison discards duplicate counts: one copy of a row can match several copies. This is the Multiplicity Blind Spot. Multiset-EX preserves counts while ignoring row order. BIRD’s set-collapsing evaluator has this limitation; Spider’s test-suite evaluator already compares multisets. Source: v1 §2.2

Can a runtime check improve SQL results without replacing the generation pipeline?

ModularSQL runs after selection. Its detector inspects execution errors, empty outputs, and excessive duplication without an LLM. Unflagged queries pass through. Full rescue selects among upstream candidates before DISTINCT patches; candidate-free use needs only the selected SQL and database access. Source: v1 §3.1, v1 §3.3, v1 §4.3

Is adding DISTINCT always a safe fix for duplicate SQL results?

No. Duplicates can be legitimate, and DISTINCT with LIMIT can change even the distinct result values. The patches target DISTINCT-level changes, not general join or aggregation repair. Normal-looking semantic errors can escape detection; duplication or an empty result does not establish incorrectness. Source: v1 §3.2, v1 §3.1, v1 Limitations

What accuracy gain and runtime cost were measured for a multiplicity guardrail?

On 1,532 executable BIRD-Dev queries, the Qwen3-Coder DeepEye-SQL reproduction improved Multiset-EX from 65.86% to 67.75%, with Set-EX unchanged at 72.06%. The run flagged 77 queries, adding $0.0076 total LLM cost and 120 ms amortized overhead per query. These are run-specific measurements. Source: v1 Table 3, v1 §4.5, v1 §4.6

Does the guardrail transfer to other text-to-SQL systems?

Candidate-free detection and patches improved Multiset-EX by 10 queries for DAIL-SQL+GPT-4 and 8 for BIRD GPT-3.5-turbo, with unchanged Set-EX. Full candidate-based rescue was tested only with the DeepEye-SQL reproduction. Evaluation covers BIRD-Dev and SQLite, not production database engines. Source: v1 Table 2, v1 Limitations

How can I try a duplicate-sensitive SQL evaluation example without a model or API key?

The public repository’s synthetic SQLite example runs with Python 3.9+ and the standard library. It illustrates set-versus-bag comparison without API keys, benchmark data, or an upstream checkout. It does not run the guardrail or reproduce the paper’s benchmark results; the README links separate reproduction scripts and dependencies. Source: Public README: synthetic example, Public README: reproduction scripts
